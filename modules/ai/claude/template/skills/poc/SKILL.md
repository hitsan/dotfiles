# poc

要求 → デモ → 要件 の順で、`/build-next` のループに入る準備を人間と進める。言葉で要件を詰める前に、決め打ちのデモで操作を体験してもらう。要件を受け取ったら、SPEC.md と BACKLOG.md は確認を挟まずに AI が書く。人間が途中でやめたら、そこまでの成果物を残して止まる。

既に `SPEC.md`・`BACKLOG.md` があれば、新しい要求の分だけ足す（手順は同じ）。BACKLOG.md の todo にタスクを足したら、レビューし直すため `REVIEW.md` があれば消す。

## 手順

1. **要求**：作りたいものを一言で言い直し、動作がわかる操作シナリオを提示する。数は要求に合わせる。OK をもらう。
   - 例（ls）: `ls` でカレントの中身 / `cd` 後の `ls` で表示が変わる / `ls <パス>` で指定先の中身
2. **デモ**：シナリオだけを体験できる単一 HTML を作る（下の「デモの作り方」）。
   - Artifact ツールが使えれば公開してリンクを渡す。使えなければ `poc/demo.html` に書いてパスを伝える。
   - 「試して、気になった点を教えてください」と伝えて待つ。フィードバックが動作の変更ならデモを直して再度試してもらう。違和感が無くなるまで繰り返す。
3. **要件**：人間が要件（デモへのフィードバックを含む）を伝えたら、次の 1〜2 を確認なしで書く。
   1. **SPEC.md**：シナリオ・フィードバック・要件から「SPEC.md の形式」で書く。
   2. **BACKLOG.md**：既存コードと `tests/` を読み、完了条件を 1 タスク = 1 コミットの大きさに分けて書く。
   3. **見せる**：SPEC.md の要点とタスク一覧（ID・やること・after）を表で見せる。「質問」が残っていれば 1 つずつ聞いて反映する。直しを言われたら反映する。
   4. **テスト**：各タスクの `test:` のテストが無ければ、タスクごとにテストの下書きを見せ、OK をもらってから `tests/` に書く。テストが何を確かめるかを 1 行で添える。人間が「自分で書く」と言ったものは一覧に残す。
   5. **設定**：「プロジェクト設定」を入れる。
   6. **コミット**：`SPEC.md`・`BACKLOG.md`・`tests/`・`.claude/settings.json` の差分を見せ、OK をもらってコミットする（`/build-next` は作業ツリーが clean でないと止まる）。デモの HTML はコミットしない。
4. **案内**：「終了時の案内」を実際の数字で埋めて伝え、止まる。実装コードは書かない。

## デモの作り方

入力に対する出力は決め打ちでよい。見せるだけなので実装しない。

- 対象の見た目をまねる。CLI なら偽ターミナル、Web なら画面そのもの。
- 状態はページ内の変数だけで持つ（登録・移動などの結果が次の操作に反映される程度）。
- 画面に置くもの:
  - 「決め打ちのデモで、実装はない」という一文
  - シナリオのチェックリスト（試すと付く）と、入力欄に入れられるコマンド例
  - シナリオ外の操作をしたら「未定義」と表示し、「エラー？上書き？」のような問いの形で一覧に記録する。要件の抜けを見つけるため
  - 操作の結果として変わる外部状態があれば、それも見せる（例: 設定ファイルの中身）
- 初期状態にサンプルデータを入れ、開いてすぐ試せるようにする。
- デモの HTML は本実装に流用しない。

## SPEC.md の形式

- シナリオとフィードバックで決まった動作 → 完了条件。「テストかコマンドで確かめられる形」に言い換える。曖昧な条件（「使いやすい」など）はそのまま残さない。
- 試さなかった・要らないと言われた操作 → やらないこと
- デモで未定義のまま決まらなかった操作 → 推測で埋めず、BACKLOG.md の「質問」に回す

```markdown
# SPEC

## 目的
<何を作るか。1〜3 行>

## やらないこと
- <範囲外にするもの>

## 完了条件
- <テストかコマンドで確かめられる形で書く。例: `cli summarize sample.csv` が tests/fixtures/expected.json と同じ出力を返す>
```

## タスク行のルール

- ID は `T1`, `T2`, ... の連番。
- `test:` に、完了を確かめるテスト（テストファイル名・テスト名、または実行コマンドと期待結果）を書く。確かめられないタスクは作らない。
- `after:` に、先に done になっている必要があるタスク ID を書く。無ければ `-`。
- 並列実行されるため、同じファイルを触るタスク同士は `after:` で順序を付ける。
- SPEC から判断できない点は推測で埋めず「質問」に書く。

## BACKLOG.md の形式

```markdown
# BACKLOG

## todo
- [ ] T1: <やること> — test: <確かめるテスト> — after: -
- [ ] T2: <やること> — test: <確かめるテスト> — after: T1

## done

## blocked

## 質問
- <SPEC から判断できない点>
```

## プロジェクト設定

このスキルのディレクトリにある `settings.json` を、リポジトリの `.claude/settings.json` にマージする。既存の設定は残し、`hooks.PreToolUse` は同じものが無ければ追加する（何度実行しても同じ結果になる）。

```sh
tpl=<このスキルのディレクトリ>/settings.json
mkdir -p .claude && [ -f .claude/settings.json ] || echo '{}' > .claude/settings.json
jq -s '.[0] as $cur | .[1] as $tpl | ($cur * ($tpl | del(.hooks))) | .hooks.PreToolUse = (($cur.hooks.PreToolUse // []) as $p | $p + ($tpl.hooks.PreToolUse | map(select(. as $h | $p | index([$h]) | not))))' \
  .claude/settings.json "$tpl" > .claude/settings.json.tmp && mv .claude/settings.json.tmp .claude/settings.json
```

入る設定:
- `autoContinueAtUsageLimit: true` — 使用量上限で止まっても、リセット後に自動で続ける。
- `worktree.baseRef: "head"` — implementer の worktree を今の HEAD（直前のラウンドで done にしたコミットを含む）から切る。
- サブエージェント（implementer など）からの `tests/` 配下の編集を exit 2 で止める PreToolUse hook。人間と対話しているメインのセッションは止めない。

普段の作業に影響しないよう、グローバルではなくこのループを回すリポジトリにだけ入れる。

## 終了時の案内

```
準備ができました（todo N 件、テスト K 件追加、人間が書くテスト L 件）。

1. 人間が書くテストがあれば書いてコミットする
   - <一覧。無ければこの項目を省く>
2. 設定を読み直すため、新しいセッションでループを始める:
     zellij attach -c autoloop
     claude
     /goal BACKLOG.md の todo が空になるまで /build-next を繰り返す。3 時間たったら止める
   zellij の Ctrl+o は Claude Code と重なるので、Claude Code 側のキーを使うときは先に Ctrl+g でロックする
3. 戻ってきたら /review でできあがりをデモ・SPEC と見比べ、/retro で振り返る
```
