# poc

言葉で要件を詰める前に、操作を体験してもらう。デモは「見せるだけ」なので実装しない。入力に対する出力は決め打ちでよい。

## 手順

1. **シナリオを決める**：要求を一言で言い直し、動作がわかる操作シナリオを 3 つ前後に絞って提示する。OK をもらってから次へ進む。
   - 例（ls）: `ls` でカレントの中身 / `cd` 後の `ls` で表示が変わる / `ls <パス>` で指定先の中身
2. **デモを作る**：シナリオだけを体験できる単一 HTML を作る（下の「デモの作り方」）。
   - Artifact ツールが使えれば公開してリンクを渡す。使えなければ `poc/demo.html` に書いてパスを伝える。
   - 「試して、気になった点を教えてください」と伝えて待つ。
3. **直す**：フィードバックが動作の変更なら、デモを直して再度試してもらう。体験に違和感が無くなるまで 2〜3 を繰り返す。
4. **SPEC.md を書く**：シナリオとフィードバックを `/plan-backlog` の SPEC 雛形（目的 / やらないこと / 完了条件）で書き、全文を見せて OK をもらう。
   - シナリオとフィードバックで決まった動作 → 完了条件（テストかコマンドで確かめられる形）
   - 試さなかった・要らないと言われた操作 → やらないこと
   - 決まらなかった未定義の操作 → 推測で埋めず、完了条件の後に「未決」として残す
5. **案内**：「`/plan-backlog` で BACKLOG とテストを作って開発ループへ進めます」と伝えて止まる。

## デモの作り方

- 対象の見た目をまねる。CLI なら偽ターミナル、Web なら画面そのもの。
- 状態はページ内の変数だけで持つ（登録・移動などの結果が次の操作に反映される程度）。
- 画面に置くもの:
  - 「決め打ちのデモで、実装はない」という一文
  - シナリオのチェックリスト（試すと付く）と、入力欄に入れられるコマンド例
  - シナリオ外の操作をしたら「未定義」と表示し、「エラー？上書き？」のような問いの形で一覧に記録する。要件の抜けを見つけるため
  - 操作の結果として変わる外部状態があれば、それも見せる（例: 設定ファイルの中身）
- 初期状態にサンプルデータを入れ、開いてすぐ試せるようにする。

## ルール

- デモの HTML は本実装に流用しない。
- このスキルでは実装コードを書かない。
