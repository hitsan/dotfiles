# review

ループで作られたものを、人間と一緒に確かめる。タスクごとの PR はループ中に人間が少しずつレビューしているので、ここでは残りだけを見る。テストが通っていても、体験がデモや SPEC とずれていないかはここで見る。判定するのは人間で、AI は動かして・見せて・ずれを整理する。

PR のレビューはコメントで表す（`/build-next` と同じ）: `OK` で始まればレビュー済み、`修正:` で始まれば修正の依頼。

## 手順

1. **読む**：`SPEC.md`・`BACKLOG.md`・`git log` と、今の branch（土台）へのマージ済み PR（`gh pr list --base <土台> --state merged --json number,title,comments`）を読む。どちらかのファイルが無ければ「先に `/poc` を呼んでください」と伝えて止まる。todo が残っていれば、その件数を伝えてから続ける。
2. **テスト**：プロジェクトのテストを実行し、結果を 1 行で示す。
3. **未レビューの PR**：`OK` も `修正:` もコメントされていない PR を 1 件ずつ見せる。
   - PR の URL と、説明 artifact の該当節（`BACKLOG.md` の `説明:` の URL に `#T<n>` を付けたもの）を示し、試し方のコマンドを実行して出力を見せる。
   - 人間の判定を聞き、OK をもらってから PR にコメントする（`gh pr comment <PR> --body "OK"` か `"修正: <内容>"`）。
   - 修正の依頼は、`/build-next` の手順 2 と同じ形式（`from:` にそのコメントの URL）で BACKLOG.md の todo に足す。ループが二重に足さないようにするため。
   - リモートが無ければ、`git log` のタスクごとのマージコミットを見せ、修正の依頼は `from:` を付けずに todo に足す。
4. **動かす**：SPEC.md の完了条件のうち、3 までのレビューで確かめていないものを 1 つずつ、本物の実装で実行して結果を見せる。
   - CLI なら実際のコマンドと出力。画面があれば起動して見せる。
   - `/poc` のデモ（Artifact のリンクか `poc/demo.html`）が残っていれば、同じ操作のデモ側の結果と並べる。
   - 人間にも実際に触ってもらうよう促す。
5. **表にする**：完了条件ごとに `OK` / `ずれ` / `未確認` と、ずれの中身を表で示し、人間に判定してもらう。
6. **戻す**：ずれごとに直し方を提案し、OK をもらって反映する。
   - 実装がずれている → BACKLOG.md の todo にタスクを足す（`test:` 付き。形式は `/poc` のタスク行のルールに従う）。
   - 要件のほうが違っていた → SPEC.md の完了条件を直し、必要なタスクを足す。
   - タスクを足したら `REVIEW.md` があれば消す（次のループのあとでレビューし直すため）。
7. **記録**：タスクを足さずに終わったら、`REVIEW.md` に結果を書く（下の形式）。
8. **コミット**：差分を見せ、OK をもらってコミットし、リモートがあれば push する。
9. **案内**：タスクを足したなら「`/build-next` のループを回してから、もう一度 `/review`」、足していなければ「main への PR をマージして、`/retro` で振り返り」と伝えて止まる。未レビューの PR が残っていれば、その件数も添える（マージは止めない）。

## REVIEW.md の形式

```markdown
# REVIEW

## <YYYY-MM-DD>
- テスト: <通過件数 / 全件>
- PR: <OK 件数 / 全件>。修正の依頼: <PR 番号と内容。無ければ省く>
- OK: <完了条件>
- 未確認: <完了条件と理由>
- メモ: <人間のコメント。無ければ省く>
```

autoloop-nav はこのファイルがあるかどうかで、レビュー済みかを判断する。

## ルール

- 実装コードは書かない。直すのはループに任せる。
- `tests/` は人間の持ち物。テストの誤りを見つけたら、直し方を提案して人間の OK をもらう。
