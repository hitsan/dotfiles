# review

ループで作られたものを、人間と一緒に確かめる。テストが通っていても、体験がデモや SPEC とずれていないかはここで見る。判定するのは人間で、AI は動かして・見せて・ずれを整理する。

## 手順

1. **読む**：`SPEC.md`・`BACKLOG.md`・`git log` を読む。どちらかのファイルが無ければ「先に `/poc` を呼んでください」と伝えて止まる。todo が残っていれば、その件数を伝えてから続ける。
2. **テスト**：プロジェクトのテストを実行し、結果を 1 行で示す。
3. **動かす**：SPEC.md の完了条件を 1 つずつ、本物の実装で実行して結果を見せる。
   - CLI なら実際のコマンドと出力。画面があれば起動して見せる。
   - `/poc` のデモ（Artifact のリンクか `poc/demo.html`）が残っていれば、同じ操作のデモ側の結果と並べる。
   - 人間にも実際に触ってもらうよう促す。
4. **表にする**：完了条件ごとに `OK` / `ずれ` / `未確認` と、ずれの中身を表で示し、人間に判定してもらう。
5. **戻す**：ずれごとに直し方を提案し、OK をもらって反映する。
   - 実装がずれている → BACKLOG.md の todo にタスクを足す（`test:` 付き。形式は `/poc` のタスク行のルールに従う）。
   - 要件のほうが違っていた → SPEC.md の完了条件を直し、必要なタスクを足す。
   - タスクを足したら `REVIEW.md` があれば消す（次のループのあとでレビューし直すため）。
6. **記録**：タスクを足さずに終わったら、`REVIEW.md` に結果を書く（下の形式）。
7. **コミット**：差分を見せ、OK をもらってコミットする。
8. **案内**：タスクを足したなら「`/build-next` のループを回してから、もう一度 `/review`」、足していなければ「`/retro` で振り返り」と伝えて止まる。

## REVIEW.md の形式

```markdown
# REVIEW

## <YYYY-MM-DD>
- テスト: <通過件数 / 全件>
- OK: <完了条件>
- 未確認: <完了条件と理由>
- メモ: <人間のコメント。無ければ省く>
```

autoloop-nav はこのファイルがあるかどうかで、レビュー済みかを判断する。

## ルール

- 実装コードは書かない。直すのはループに任せる。
- `tests/` は人間の持ち物。テストの誤りを見つけたら、直し方を提案して人間の OK をもらう。
