# retro

ループとレビューの結果を振り返り、残った問題を次のループに渡せる形にする。

## 手順

1. **要約**：`BACKLOG.md` の done / blocked / todo の件数、`git log` のタスクごとのマージ、`REVIEW.md` の結果を短く見せる。`REVIEW.md` が無ければ「先に `/review` を呼ぶと、できあがりを確かめられます」と添える。
2. **blocked を立て直す**：`blocked` が残っていれば、下の「blocked を立て直す」を行う。
3. **振り返り**：fail の理由やレビューで見つかったずれから、繰り返し起きた問題を 2〜3 点挙げ、次に SPEC やテストを書くときの注意として示す。
4. **コミット**：変更があれば差分を見せ、OK をもらってコミットする。
5. **案内**：todo があれば「`/build-next` のループを回してから `/review`」、無ければ「追加があれば `/poc` で要求から伝える」と伝えて止まる。

## blocked を立て直す

1. `blocked` の各行の理由と、関係する差分・テストを読み、原因を「SPEC が曖昧」「テストが誤り」「タスクが大きすぎる」「依存の漏れ」などに分けて示す。
2. 直し方（SPEC の修正、テストの修正、タスクの分割、`after:` の追加）を提案し、OK をもらって反映する。動作の認識がずれていそうなら、`/poc` の「デモの作り方」で該当シナリオのデモを作って確かめる。
3. 直したタスクを `todo` に戻し、行末の `fail:` を消す。
4. todo にタスクを戻したら、`REVIEW.md` を消す（次のループのあとでレビューし直すため）。

## ルール

- 実装コードは書かない。
- `tests/` は人間の持ち物。直すときは人間の OK をもらう。
